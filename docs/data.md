# Data and interfaces

## Local persistence

IndexedDB voltura-places version 1 contains partitioned workspaces and drafts. Keys are guest or verified account ID. Entities have stable ID, kind, value, server revision, deletion flag, local generation, dirty flag and optional preserved conflict. Changes/pending state commit atomically before success. Capacity: 5,000 live places, 200 live categories.

Places contain name, optional trimmed description (up to 1,000 characters), categoryId, WGS84 latitude/longitude, nullable accuracy in metres, capturedAt and updatedAt. Categories contain a canonical fallback name, optional names with bounded en/sv translations, semantic color, optional validated icon identifier and optional built-in translation key. Each translation is trimmed and 1–60 characters; at least one is required when names is present, and other languages/keys are rejected. Display uses the selected app language, then the other supplied name, then the legacy canonical fallback. Untouched built-in presets retain their existing translations. Translation objects survive account/group sync, guest transfer and backup/import. Source versions before 0.1.13 must update before reading categories with names, because their strict schema rejects that new optional field. No database migration or backup-version change is required. Icons follow atomic local writes, sync, group copying and backup/import. Missing icons use presentation defaults without rewriting records. Explicit `icon: "none"` suppresses the icon without falling back to the place pin or a built-in icon; it follows normal local writes, sync and backups. Legacy amber Mushrooms displays rose until its appearance is explicitly saved. The category catalog supports 12 semantic colors and 48 pictograms plus the explicit no-icon identifier `none`. Older strict-schema app versions, including synced devices and backup recipients, must update before reading newly added appearance values; older backups remain supported. The catalog expansion requires no database migration. Missing/deleted categories display/export as Other. Local category deletion moves its places to Other in the same transaction.

Preset revision 2 adds Mushrooms/Svampar to existing workspaces atomically on first read, without changing renamed categories, tombstones, drafts or in-flight requests. It queues the new category for reconciled accounts. Full category libraries defer the addition until a slot is available. Later deletion of this preset is respected. New workspaces start with all six presets.

Editor saves commit the record, pending state and removal of that record's matching draft in one transaction. Place deletion also removes only its matching draft atomically. Queued draft writes settle before these operations and before account/device removal enumerates partitions. A draft cleanup failure rolls back the record change rather than leaving a successful save behind an error. Explicit transaction failure paths abort and consume transaction completion failures, including failure of the initial read; draft/photo cleanup failures retain their original data and report the operation failure. Local entity writes validate the shared schema before committing.

An editor retains its original value as a comparison base. If a clean cloud record changes or is deleted while the editor is open, saving preserves both the edited and current cloud versions as a conflict. A stale editor cannot overwrite a newer unsynced edit from another tab. Editing an existing conflict retains its recovery version; Keep both creates a fresh record without inheriting the original conflict metadata.

Editor/category saves, conflict choices and group-copy record commits recheck their originating operation's cancellation inside the write transaction, including after queued drafts and record writes. A cancelled transaction retains the previous record and matching draft. Device-to-account copying also rechecks after destination and guest-receipt writes, rolling both back together. A save already committed before a library change stays in its original library; late UI completion does not open that record in the new library.

Application operation validity includes account/workspace generations, not just identity/key equality. An A → B → A transition cannot revive a pending save, import, read, synchronization response or UI completion from the earlier visit to A. Export preparation uses the account generation so changing libraries alone does not cancel an export. These guards supplement the existing transaction predicates and server authorization; they do not change stored data or wire formats.

## Personal visit status

Personal `visit` entities are stored in the guest workspace or the signed-in person's private workspace, never a group workspace. Values contain `placeId`, nullable group `libraryId` (null for private/device places), `status` (`none`, `want`, `visited`) and `updatedAt`. IDs are `visit-` followed by SHA-256 of the UTF-8 JSON pair `[libraryId,placeId]`; personal account partitioning isolates identical references between members. Missing status means none. Existing places are not retroactively classified. Saving a current GPS position, including explicit GPS selection in the editor, writes Visited automatically. Photo coordinates and manual/shared places do not imply a visit. Name/description edits preserve personal status.

A GPS place save and its private status commit in the same IndexedDB transaction, including group saves and matching draft cleanup. Storage failure, an import lease or scope cancellation rolls both back. Status-only changes never dirty the group place. Clearing status persists a `none` record so it can sync. Metadata survives a shared place's disappearance, but is displayed/exported only for visible live places. Device-to-private transfer remaps personal statuses with destination IDs without claiming another account's statuses. Group copies retain the description but start without a personal status for the new identity.

Migration 0009 adds `places_visits`, keyed by the actual authenticated account with account-deletion cascade. It uses the existing private sync CAS/revision/receipt path and is combined with private records for sorted snapshot pagination. Group snapshots exclude visits and group writes reject them even for owners. The server validates canonical visit IDs; ordinary place/category IDs cannot use the reserved `visit-` prefix. The live personal-status limit is 100,000, independent of place/category capacities. Snapshots are bounded to 200,000 total records including tombstones; mutation batches allow 105,200 writes. Same-record status conflicts preserve both values for an explicit Keep device/Keep cloud choice; Keep both is unavailable for personal status.

New descriptions and the new entity kind require current clients before synchronizing or importing newly exported backups; older strict-schema clients cannot read them. Apply the migration and deploy the validated server/client together. Existing records and older backups remain readable without rewriting stored data.

## Sync v1

GET /api/v1/sync returns `{version:1,accountId,records}`. POST accepts `{version:1,mutationId,baseRevision,deleted,entity}` and returns the accepted record or 409/current record. Require a Places session and matching X-Places-Account header. Writes also require the canonical Origin.

Reads use 250-record pages with `nextCursor`; pass it as `?after=` for the next page. Pull up to 200,000 records including personal statuses and deletion history, so tombstones do not consume the live-place capacity. A boundary failure preserves the local workspace. `shared/limits.ts` owns page, snapshot, mutation-batch and live-entity capacities for schemas, browser persistence and server enforcement.

Per-workspace sync requests coalesce while a run is active. A current queued request survives cancellation of the previous view; cancelled callers cannot replace or restart queued work. An active caller retains its status subscription across the follow-up run.

Persist exact in-flight bodies before network access. D1 atomically commits CAS record changes and body-hashed receipts. Same-ID/same-body retries return receipts; changed bodies are rejected. Tombstones/receipts persist until account deletion. Device clocks never select winners.

Independent record edits merge. Identical concurrent writes converge on the cloud revision, preserving any newer device edits. Different same-record conflicts retain both versions. Keep device rebases on the cloud revision; Keep cloud accepts it; Keep both accepts cloud and creates a fresh device identity. Guest/account workspaces and pending writes remain partitioned. Sign-in automatically merges new guest places, photos and categories into Private places, regardless of group membership or the selected group. There is no storage-choice dialog. Account snapshots are validated before setup; reconciled workspaces retain their pending writes. Stable destination identities derive from account/source IDs, and existing receipts and cloud tombstones prevent duplicate imports or resurrection.

Guest workspace deviceTransfers binds each handled source ID to one account, destination ID and source generation. The private records, pending writes, account guestPlaces receipts, ownership and device account history commit atomically after photo preparation. A failure or cancellation commits none of those record/ownership changes. Legacy per-account receipts and matching legacy copies are adopted conservatively without reimporting them into another account. Ownership survives removal of the account's local cache and remains after source cleanup; only the owning account can finish a pending transfer.

Guest originals remain until the private destination has a confirmed cloud revision, no dirty state, conflict or pending flight, and the source generation still matches. When the guest source has a personal status, cleanup also waits for its live destination's mapped private status to reach a confirmed cloud revision with no conflict or pending write. Cleanup removes the place, its guest status and its matching draft together in one IndexedDB transaction after queued drafts settle. Unrelated or newer guest records/drafts remain. Guest categories and unreferenced cached photo bytes are not removed by this record cleanup; they cannot create a new account import without a source record. Failed/offline saves retain the originals and pending private writes; an inline Retry action resumes the same transfer. Skip for now defers the failure UI for that account session, leaves a reminder with Retry, and enables normal account use. An available verified account snapshot is initialized separately so a transfer-capacity failure does not hide existing private places. Offline private edits survive initialization and use the normal conflict rules. An edit made to a guest source while its transfer is pending is retried as an independent private copy, preserving edits to the earlier destination. A previously skipped source generation cannot be finalized against a different private copy after local account cache removal. Skipping does not discard records, undo pending writes or release existing ownership; already-queued account writes can still sync normally. Reloading attempts the transfer again. Successful completion shows the transferred count, for example “3 places added to Private places.” Switching accounts cancels the former UI operation and cannot claim its pending originals. The local metadata is backward-compatible and requires no database or server API migration; browser-data deletion still removes local-only recovery state.

Snapshot pages reject duplicate identities, identities behind the requested cursor and continuation cursors that do not match the last and greatest returned ID. A pull cannot change an existing record's kind or roll back its revision or preserved conflict. Successful mutation acknowledgements verify the requested identity, kind, deletion, next revision and canonical value. Updates without a photo field can retain a server-side attachment for compatibility. A server missing a previously acknowledged attachment triggers one re-upload and retry of the exact place mutation. Acknowledgements likewise reject kind changes and retain newer cloud conflicts or an already accepted newer cloud version. Equal record values compare independently of object-property insertion order. New deletion markers remain writable when live capacity is full. Missing optional presets are added only while category capacity allows. A discarded synchronization operation cannot report a new status into its former view.

Value equality follows the schemas' JSON representation, recursively including localized category names: optional undefined fields match omitted fields, while explicit null remains distinct (including photo removal). Existing in-flight bodies and mutation identities are not rewritten by comparison. Final sync status includes local edits received while attachments were downloading. Migration 0008 adds a covering `(kind,deleted,account_id)` record-count index for capacity and aggregate queries; it changes no records, authorization, revisions or API format and is compatible with older code.

Denied or unavailable Web Locks fall back to the same transactionally persisted flight and server-receipt path. Account/workspace cancellation is checked between snapshot pages, preventing discarded pulls from fetching additional pages.

JSON write bodies must be bounded UTF-8 objects with an application/json media type. Malformed JSON/encoding or non-object bodies return 400, unsupported media types return 415, oversized bodies return 413, and entity/action schema failures return 422. Sync and group endpoints preserve these client-error statuses without changing stored data.

## Backup and sharing v1

Backup JSON: `{format:"voltura-places",version:1,exportedAt,places:[{id,value}],categories:[{id,value}]}`. Backups with photos use version 2 and add `photos:[{id,data}]` with JPEG data URLs; version 1 remains supported. An optional `visits:[{placeId,status}]` array holds only the exporting person's statuses for the exported live places, including group backups. Descriptions remain inside place values. Exclude credentials, drafts, sync operations, revisions and tombstones. Require finite coordinate ranges, bounded names, unique IDs, an Other category, valid category references and complete, valid photo attachments. Files are limited to 112 MiB to accommodate base64 photos and escaped place text at full library capacity.

Validate completely before one transaction. Merge retains conflicting existing values and gives incoming copies new identities; Replace tombstones missing entries. Import then uses normal sync. Status references are fully validated and remapped with copied place identities. Group imports write statuses to the importing person's private workspace atomically with shared records; no status is exposed to group members. Private merge preserves an existing personal choice; Replace restores supplied choices without clearing unrelated group statuses. Older backups without statuses preserve existing choices. Reject unknown versions without modifying storage. New versions require documented compatibility.

Shared links: `/#place=<base64url UTF-8 JSON>` containing `{version:1,name,category,latitude,longitude}` and an optional description. Personal status is excluded. Fragments are bounded to 12,288 characters. Validate and remove the fragment from the address bar after reading. Anyone holding the original link can read it; no expiry/revocation. Saving creates a new identity.

Merge imports preserve existing deletion markers by recovering incoming deleted identities under new IDs. Place/category ID collisions are remapped in both merge and replace modes, including category references. Unchanged categories do not create unnecessary pending writes. Incoming share fragments are consumed on launch and subsequent hash changes; malformed place fragments are also removed after validation.

## Family libraries

Migration 0003 introduces shared family libraries. Migration 0005 preserves existing memberships while allowing an account to belong to up to twenty groups, each with at most ten members. Every group has its own non-login storage account, records, photos and mutation receipts. The owner manages that group's membership; every member can read/add/edit/delete its shared content. Personal records remain separate. Share → Share with a group and Copy to group let the user choose another active group from either private places or an active group. The current group is excluded. Copying creates an independent record/photo copy and matches categories by name; it does not move or subsequently mirror the original. Account/library changes or lost source/destination membership cancel uncommitted copies. The destination uses its existing atomic pending-write and server-authorized sync path.

`GET /api/family` returns the `families` array, member identity labels and an optional pending request. Group management mutations require an explicit `familyId`; create returns the affected ID alongside the current list. `POST /api/family` with `action: "rename"`, `familyId` and `name` trims and validates a 1–80-character name, then changes only the selected group's name. Both the authorization check and SQL mutation require current ownership and membership; a lost authorization returns 403. Renaming preserves group identity, members, invitations and all shared records/photos, requiring no migration. There is no implicit primary group or parallel single-group API. Authentication and `X-Places-Account` always identify the actual person. Sync/photo requests additionally supply `X-Places-Family`; the server resolves membership to storage ownership. SQL reads and CAS/photo writes include membership predicates. Revisions, tombstones, conflicts and idempotency apply independently in each library. Joining another group does not leave an existing one.

The default invitation is a four-digit code entered inside the recipient's own installed app under Family sharing. Migration 0004 stores hashed, unique active codes, pending requests and attempt counters in the same D1 database. New codes have no time limit and are consumed by one successful approval or cancellation. The existing numeric expires_at/expiresAt field uses zero for no expiry; previously issued timed codes keep their original expiry. Pending requests stay available until approval, rejection, rotation or cancellation. Entering a code requires sign-in and creates a request, granting no membership, locations, family name or photos. Only the current owner can see requesting identity labels and explicitly approve or decline. Approval atomically checks the current code, any legacy expiry, membership capacity and owner; then consumes the code and cancels other requests. Rotation/cancellation clears pending requests. Codes are not access credentials; owner approval is essential because four digits can be guessed.

Code entry and generation are limited independently to five attempts per account per fifteen minutes, plus twenty per trusted proxy IP where available. Only a hash of that IP is stored in bounded, expiring rate-limit state. At most five pending requests are retained per code. Family settings poll every five seconds while visible/online, without overlapping requests, so owners see requests and recipients see approval. No code is logged or retained in browser storage.

Code request plus owner approval is the sole group invitation mechanism. Migration 0006 removes unused URL invitation tokens; existing memberships and place/photo data remain. Old group-invitation links no longer grant access. Location snapshot sharing links remain a separate feature. No messages are sent by the app.

Local workspace/draft/photo keys are `family:<signed-in-account-id>:<family-id>`, separating each person's cached data and pending writes. The metadata cache migrates older single-group entries and retains every known active or read-only group. Normal launch, foreground, reconnection and visible-page polling synchronize the selected library. Offline writes queue normally. After membership ends, the last downloaded copy remains readable/exportable locally and cloud operations are denied for that group. Removal cannot recall downloaded copies or exports, and does not affect another group's membership or records.

Visible-page polling refreshes memberships as well as records. The selected group keeps its stable identity and metadata when other groups are added, removed or joined elsewhere. Account transitions discard transient dialogs and cancel pending import/reconciliation/photo work. Sync responses received after a workspace is deselected cannot acknowledge or restore its data; the persisted flight remains available for an idempotent retry if that account returns.

An owner must transfer ownership or delete each group they own before deleting their account; leaving an owned group requires resolving that group first. Family deletion cascades shared cloud data and memberships, preserving personal libraries. Existing photo limits apply separately to shared storage. Account/device removal clears that person's local private and family partitions without clearing another person's copies.

An existing invitation applicant can repeat their request when all five pending slots are occupied, without taking an additional slot. Automatic device copying that fails for a library/photo limit or a missing source photo offers the explicit keep-on-device choice, allowing account-only access while preserving guest originals.

## Privacy/recovery

On launch, Places checks persistent-storage permission and requests it automatically when supported and not already granted. This best-effort browser request never blocks launch or local saving; denial, missing APIs and errors are tolerated. Backup settings retain a manual retry. The browser decides whether to grant persistence; this is neither encryption nor a backup, and explicit clearing of website data still removes local copies.

GPS is explicit, never background-tracked. No end-to-end encryption claim. The app does not encrypt local copies/exports. Cleared browser storage loses unsynced data; cloud sync and exports provide recovery. Account deletion cascades records, identities, sessions and receipts.

Sign-out invalidates both the Places session and the short-lived Better Auth proof session. A pending offline logout is account-specific; a server account-change response clears the stale marker instead of trapping the next account in a retry loop. Disabled account configuration denies family/photo capabilities as well as personal synchronization.

Account metadata changes in another tab trigger a fresh account check. Browser settings-storage failures do not prevent online account discovery; a failed logout retains an in-memory retry marker when browser settings cannot persist it. Export preparation and photo retrieval stop when their originating account is discarded.

An archived group keeps its display name and library ID for offline viewing and export. Its archived metadata omits participant and applicant identities and invitation state. The next successful membership refresh also removes that information from older archived cache entries.

## Database structure and normalization

Accounts, provider identities, sessions, groups, memberships and invitation requests are relational, with foreign keys and account-deletion cascades. Group storage has a separate account identity; membership authorizes access rather than duplicating records per member. Personal visit records remain in private storage even when their place belongs to a group. Photos are separate immutable blobs referenced by ID, keeping binary data out of ordinary record snapshots.

The record value is intentionally a validated JSON aggregate with a stable identity, kind, revision, tombstone and last mutation. The whole aggregate is the compare-and-swap unit. Splitting its fields into separate tables would require joins/reassembly for every offline snapshot and would not remove a demonstrated update anomaly in this access pattern. Category references deliberately tolerate missing/deleted categories and display Other, because independently synchronized records and tombstones can arrive in either order. A strict cross-record foreign key would prevent those valid recovery states.

Receipts deliberately retain the accepted record as an immutable response snapshot: a retry must return its original result even after the live record changes. Their duplication is required by idempotency. Browser workspaces similarly retain records, pending flights, conflicts and transfer receipts together for atomic recovery; photos remain in their separate store. This refactor introduces no migration, database version or persisted-format change. Very large workspace documents still incur IndexedDB structured-clone costs; changing that layout requires a separately measured, migration-tested design.

## Photos

JSON and JPEG bodies share a bounded byte reader. It checks actual streamed byte counts rather than trusting Content-Length, avoids an unbounded array of chunks, cancels failed/oversized reads and releases its reader lock. Malformed UTF-8 remains a client error. Endpoint-specific status codes and photo validation remain separate from transport parsing.

Photo reads check workspace cancellation before storage access and again before returning cached bytes or starting a download. Download responses recheck cancellation before decoding/persistence; upload responses recheck it before marking local bytes uploaded. Discarded operations leave the existing image and pending upload available for retry.

Upload acknowledgement rechecks cancellation within its own IndexedDB transaction. Photo preparation stops at asynchronous decode/encoding boundaries when its editor is discarded. A missing cloud attachment leaves sync needing attention but no longer prevents other referenced photos from downloading; cached attachments require only an identity scan during pulls.

Photo writes recheck cancellation inside their transaction. Open photo views observe newly stored bytes and retry on reconnection. Upload preparation recovers an already-cloud-backed photo when its local blob is missing. Copying into another workspace remaps colliding photo IDs when the bytes differ, reuses an equal destination image when available, and preserves both original images.

Places optionally reference one immutable `photoId`. Camera/library inputs decode and re-encode to JPEG (maximum 1280 pixels per side, 256 KiB), stripping source metadata. Separate IndexedDB `voltura-places-photos` version 1 stores workspace-partitioned blobs without blocking older tabs on a main-database upgrade. Persist the photo before its place/draft reference; interrupted writes can leave an unreferenced photo, never a successful place save without its local photo.

The client reads GPS locally from the selected original image with the pinned MIT library exifr. Only an explicit Use photo location action changes the place position; camera metadata itself is not uploaded. Missing, malformed or picker-stripped metadata is a normal fallback. Browser image decoding still determines which image formats can be attached.

Private `/api/v1/photos/:id` GET/PUT requires the session and expected account; PUT also checks canonical Origin, bounded JPEG headers/dimensions and immutable content hash. D1 migration 0002 stores blobs in the existing database. Upload photos before syncing their place references and download referenced cloud/conflict photos for offline use. `X-Places-Photos: 1` opts into photo references; older clients receive compatible records and their edits preserve existing photos.

Each workspace/account permits 50 MiB and 1,000 stored photos. Replaced/removed image blobs remain private until account deletion or local workspace removal, and count toward this limit. Account deletion cascades cloud photos. Shared snapshot links exclude photos. Guest photos cross into an account only through explicit guest-library reconciliation. Photo backups validate before writing; storage failures preserve existing places.

## Recovery follow-up — 0.1.2

Editor drafts retain the original entity comparison base; legacy restored drafts with no trustworthy base preserve a conflicting current version instead of silently overwriting it. Discard removes only the matching draft identity. Snapshot merge, mutation preparation and acknowledgements recheck workspace cancellation inside their IndexedDB transactions. Identical higher-revision pull values converge without conflict.

A capacity-rejected exact mutation can be deferred durably while freeing deletion mutations run, then resumes with its original request ID/body. Uncertain network failures retain the original flight. Deferred flights block imports just like active flights.

Photo-free imports commit directly in one record transaction without scanning cached attachments. Imports with photos validate merged capacity before persisting photo bytes. When a group backup contains personal statuses, one transaction reserves capacity in both the group and the importing person's private workspace until the final record commit. Imports recheck currently known group write access during asynchronous photo preparation and inside the record transaction; revoked access disables confirmation and prevents record changes. Reservations expire after five minutes after interruption and are removed without recreating a deleted workspace. Concurrent writes during an active reservation return syncBusy. Browser decoding verifies imported/downloaded image data in addition to shared JPEG table/frame/scan structural checks; photo decoding is sequential to bound phone memory. Photo ID collisions reuse equal destination bytes so repeating the same backup does not add duplicate places. Group copying recovers cloud-backed source photos and reuses categories by name, preferring an exact translation and appearance match when names collide.

Group responses expose an opaque, secret-derived invitation version to the current owner only, or null when no active invitation remains. It cannot be used as an invitation code. The owner UI compares it while polling to invalidate consumed, cancelled or rotated in-memory codes; numeric codes are still never stored in browser settings. Membership refreshes preserve the composition's in-memory inactive groups when settings storage is unavailable.

## Public usage statistics

`POST /api/v1/activity` accepts only `{browserId}` with a UUID v4. It requires the canonical app Origin and URL origin, rejects cross-site writes and bounds JSON to 128 bytes. Requests omit credentials. The server hashes the identifier with the Places secret and records server time only. Repeat reports coalesce within one minute except for the first report after Stockholm midnight. No account association, IP address, place data or browsing history is stored. Indexed entries older than 31 days are removed in batches of at most 100 during reporting; inactivity is excluded from counts immediately at each window boundary.

`GET /api/v1/statistics` returns `{version:1,generatedAt,activityStartedAt,activeNow,activeToday,active30Days,registeredAccounts,cloudPlaces,averagePersonalPlaces}`. Times are epoch milliseconds. A conditional database update caches a single aggregate snapshot for 60 seconds or until the next Stockholm midnight. Warm reads use one database read. Public responses contain aggregates only. Read CORS allows the app and `https://voltura.se`; local app configurations additionally allow `http://127.0.0.1:5175` and `http://localhost:5175`. Other supplied Origins are rejected. Activity writes never accept the promo origin.

Active now covers the last two minutes; today starts at Europe/Stockholm midnight, including daylight-saving transitions; 30 days is a rolling 720-hour window. Browser identifiers deduplicate tabs but not separate devices or cleared storage. Reporting is enabled by default and controlled by a device-local Settings → Privacy switch. Only visible, online app pages report, immediately and once per minute. Opt-out removes the local identifier and stops/aborts requests across tabs; existing anonymous activity ages out. Blocked storage uses an in-memory identifier and setting. Activity history begins when migration 0007 is applied; there is no historical backfill.

Registered accounts excludes group storage accounts. Cloud places counts undeleted place records in private and shared libraries once per stored record. Categories, tombstones and guest-only places are excluded. Personal copies and group copies are independent records. The average is private cloud places divided by all personal accounts, including empty accounts, with zero for no accounts. Counts reflect deletion after cache refresh. Migration 0007 adds only activity/cache tables and an expiry index; record and synchronization contracts are unchanged.

## Account and sync boundary handling

Migration 0010 adds a generation to each newly issued invitation. Existing codes retain their legacy owner-visible version. When the owner acts on a displayed request or revokes a displayed code, the decision includes that invitation version. The server checks it again in the membership or invitation transaction. Requests for a replacement invitation survive a delayed decision, including when randomly issued digits repeat. Older clients can continue submitting the existing unstamped actions. A rejected account or IP rate limit leaves the other allowance intact.

A browser that replaces its Places session invalidates the supplied old Places token. Starting a second link replaces that browser's earlier ticket. Redeeming a ticket requires a current session for its account. Signing out invalidates the presented session and ticket. Account deletion checks session validity and group ownership in the same transaction as identity removal. Better Auth cleanup handles both ISO and legacy numeric dates in bounded batches. The migration also indexes expiry, orphan-account and photo-capacity queries.

An empty explicitly supplied group scope is rejected. Sync receipts, record contents and photo data are read under the current session and membership. A CAS edit to an absent identity with a positive base revision returns 422. Restoring the current deletion marker when live capacity is full returns 413 with `libraryLimit`, permitting the usual deferred retry.

New identities, including deletion markers, share the workspace's 200,000-record snapshot limit across ordinary records and private visits. Reaching that history limit returns 413 with `snapshotLimit`. The client keeps the exact blocked request, allows edits to identities already present in the cloud to proceed, and reports that action is required. Each later sync pass attempts at most one unsuccessful blocked creation. Existing identities and exact receipts remain writable or retryable. The migration preserves all previous data, including any history already above the pull limit.

## Optional account display name

Migration 0011 adds a nullable display name to the Places account. Existing accounts retain their verified identity labels. The signed-in person can set or clear the name through `POST /api/account/display-name` with `{displayName}`, the canonical Origin and the matching `X-Places-Account` header. The response contains the updated account and preserves its provider methods. Names are NFC-normalized, trimmed and limited to 60 Unicode code points. Blank text or null clears a name. Embedded control characters, line separators, unpaired surrogates and bidirectional embedding, override or isolate controls are rejected.

Display names need not be unique. Members see the chosen label in their group's roster. The current owner sees it on that group's pending join requests. Clearing the name restores the existing label fallback. The display name never identifies a user for sign-in, authorization, ownership, invitation decisions, activity statistics or synchronization.
